# Limitations of BASP Dataflow v0.2

This release is a Python research system: a simulator, a scheduler, reference kernels, a
design-space explorer and calibration tooling. It contains **no hardware measurements**. Every
performance number it produces means "what the model concludes under the stated assumptions",
and the hardware gate in the report says so in its evidence column.

## Nothing is calibrated yet

* **No measurement has been taken.** The calibration scripts exist and their logic is tested, but
  the parts that touch real hardware (GPU profiling with PyTorch, running `llama-bench`, hooking a
  real model's routers, reading `.safetensors`) have never been executed. See
  [calibration.md](calibration.md).
* **The fitting procedure has only seen synthetic data** generated by the simulator itself. That
  shows the fit can recover parameters of a machine that behaves like the model; it does not show
  that a real machine behaves like the model. If validation fails on real data, the model of a
  conventional system needs work before any comparison means anything.
* **The baseline machine is illustrative.** The architecture comparison runs on
  `configs/desktop_gpu12.json` (a generic desktop with a 12 GiB GPU), not on a measured machine.
  Its parameters decide the comparison where the conventional system leans on its CPU. One of
  them was corrected in this release: v0.1 assumed 30 GMAC/s of CPU arithmetic, which made
  CPU-side decoding arithmetic-bound and roughly halved the conventional baseline for models that
  do not fit the GPU; it is now 80 GMAC/s, so that CPU decoding of dense models is limited by
  memory bandwidth, as is commonly reported for llama.cpp. That is still a judgement from public
  figures, not a measurement, and the model-size results for large models move with it.

## Estimates for hardware that does not exist

* **Compute-memory modules are hypothetical.** Their arithmetic rate (MAC lanes times an assumed
  clock), usable memory bandwidth, launch and link latencies, idle, sleep and active power are
  (pessimistic, nominal, optimistic) triples chosen by judgement in
  `configs/design_estimates.json`. Calibrating the simulator on a CPU and a GPU does not narrow
  any of them.
* **Prices are guesses**, for ratios only: no supplier quote, no volume assumption, no
  development cost. The pessimistic system price is more than twice the optimistic one.
* **The local fabric of architecture H** (a switch connecting GPU and modules with 0.5 us latency)
  is an assumption about an interconnect that has not been designed.
* **Corners are not confidence intervals.** They bound what was thought plausible; reality can
  fall outside them.

## Workload assumptions

* **Routing traces are synthetic** (Zipf popularity with per-slot stickiness). Cache hit rates,
  placement quality, imbalance and prefetch benefit all depend on real router behaviour.
  `benchmarks/record_routing_trace.py` records it; it has not been run.
* **Co-activation-aware placement is regularised towards load balancing** because short traces
  cannot estimate pairwise statistics; on the traces used here it performs like balanced placement.
  Whether real routing has exploitable co-activation structure is unknown.
* **Model shapes, not models.** The suite uses published configurations (DeepSeek-V3 approximated:
  its latent attention is a parameter count and its three dense layers are folded into the trunk)
  and two hypothetical trillion-parameter shapes. No weights are loaded and nothing is claimed
  about any model's quality.
* **Compression ratios are assumptions** for the entropy-coded, sparse-block and predictive
  formats. The entropy figures in the report are order-0 entropies of synthetic weight
  distributions.

## Modelling simplifications

* Memory is a bandwidth model: no row-buffer behaviour, refresh, NUMA or cache hierarchy.
  Ramulator2 and Timeloop are not integrated.
* A device runs one kernel at a time at its full roofline rate. Batching is modelled as a reduced
  launch cost for back-to-back kernels, not as a wider kernel. As a consequence a GPU that holds
  the whole model still gains from modules executing experts in parallel with it; a real GPU
  running one batched kernel may not leave that gain on the table.
* Link sharing is fluid (dominant-resource fairness); the estimator approximates it with
  gap-aware booking, so estimates under contention are a few percent off the simulation.
* **Results are equal within rounding, not bit for bit, across dataflows that reorder
  additions.** Policies that keep the reduction order produce bit-identical logits whatever the
  placement, transfer strategy or graph form. Device-local partial sums (output-stationary mode)
  and tensor-parallel experts add the same FP32 terms in a different order; over 60 random small
  models this changed logits of magnitude 4 by at most 8e-4 in about one run in five, and never
  changed routing. A reordered sum could in principle tip a near-tied routing decision. v0.1
  claimed bit-identity under every policy; its test passed for one seed by luck and failed on
  another platform. A hardware accumulator wide enough to make the reduction exact would restore
  the stronger guarantee; that is a design option, not something modelled here.
* The numeric co-simulation carries expert outputs and partial sums in FP32 and rounds to FP16
  only at the next kernel's input, while the traffic model charges FP16 sizes for those tensors.
  One of the two is optimistic: either that traffic is twice what is counted (it is small next to
  weight traffic), or results carry one more FP16 rounding per expert than the numerics show.
* Attention is cost-modelled (projection MACs and KV-cache traffic) but not computed numerically;
  the numeric co-simulation uses an attention-free MoE stack. Sampling and the embedding lookup
  have no cost.
* Prefill is modelled as one step with the prompt as a batch at half the prompt's context.
* Concurrent streams share devices and links but not KV-cache memory pressure.
* Power gating has one sleep state per device with a fixed wake energy; there is no DVFS and no
  thermal model.
* The scheduler takes no simulated time. Its overhead is reported as a per-decision cost budget,
  because the Python implementation's run time is not evidence about a production scheduler.
* Host-free dispatch (`host_in_loop=False`) is allowed only for static dataflows; architectures
  that cache or prefetch keep the host in the loop.
* Fault injection is limited to protocol-level checks (CRC, protection faults, version
  mismatches, timeouts).

## Design-space exploration

* The space covers architecture, GPU memory (none, 12 or 24 GiB of one assumed GPU speed), module
  count, module memory, channels, MAC lanes, link bandwidth and expert replication. The
  conventional side therefore has two points; faster or multiple GPUs are not candidates, which
  flatters module-based designs in equal-cost comparisons.
* The search optimises one workload (30B MoE, single-user decoding) at the nominal corner; front
  designs are re-evaluated at the other corners. A design that is optimal for another model size
  or workload type may not be on this front.
* The evolutionary search evaluated about a quarter of the feasible designs. It is seeded with
  the conventional systems and one standard design per architecture; it is not exhaustive.

## Not implemented

| Item | Status |
|---|---|
| `hardware/*.sv` (decoder, MAC array, accumulator, stream controller) | Not started, by decision: no RTL until the hardware gate passes |
| `backends/cuda`, `backends/metal`, llama.cpp integration | Not started; no physical performance has been measured |
| C++ production runtime | Not started |
| Real-model expert computation | Kernels and co-simulation are verified on a small random-weight model only |
| Distributed learning | Only versioned tensors with explicit synchronisation |
| INT2 / ternary / sparse / entropy *kernels* | Formats are modelled for traffic and decode cost; only INT4 has a numeric kernel |
| Hardware-aware routing | Deliberately out of scope: the runtime never changes which experts are selected |

## Known rough edges

* `Command` descriptors carry at most 8 tensor ids; longer operand lists live in the kernel
  descriptor passed alongside the command.
* Background replication and prefetch share one budget per link direction; there is no
  per-destination fairness.
* The quick report (`--quick`) uses short runs; its numbers differ from the full report's.
* Generated files are byte-identical only on the same Python and NumPy versions. Between Python
  3.10 and 3.13 simulated figures differ in the last digit (about 1e-16 relative), because the
  built-in float summation changed in Python 3.12.
* The v0.1 report in `reports/v0.1/` was produced by the v0.1 model (one GPU launch per expert,
  output projection pinned to modules) and is kept as a record only.
